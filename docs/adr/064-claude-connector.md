# ADR-064: The Claude connector is a stateless MCP server with Materia as its own OAuth server

- **Status:** Accepted
- **Date:** 2026-10-07
- **Ticket:** [INT-07](https://linear.app/materia-web/issue/MAT-185)
- **Refines:** ADR-019: Integrations, ADR-037: Clerk suggestions ([Architecture & ADRs](../01-architecture-and-adrs.md))

## Context

Lawyers who use Claude want to ask it about their matters ("what's due this week?", "summarise the Ada estate") and have it record what they ask for ("add a task to call the executor", "note this call", "log 30 minutes"). Claude connects to outside systems through the Model Context Protocol (MCP). A remote MCP server is an HTTPS endpoint that Claude calls with an OAuth access token. Claude (claude.ai and the desktop apps) and Claude Code each sign in through the server's OAuth authorization server.

This is a different shape from Clerk. Clerk runs inside Materia on the firm's own Anthropic key (ADR-011b). The connector runs in the person's own Claude account: Materia only answers its tool calls, and what it returns is processed by Anthropic under that account's terms. The person's access in Materia must be the ceiling. Privilege and the "Clerk never writes on its own" rule (ADR-037) must survive the move outside.

## Decision

- **One function, on the app's own origin.** `connector-api` (HTTPS, `australia-southeast1`) serves `/mcp`, `/oauth/token`, `/oauth/revoke` and the metadata at `/.well-known/oauth-protected-resource[/mcp]` (RFC 9728) and `/.well-known/oauth-authorization-server` (RFC 8414), through Hosting rewrites. So the MCP URL a person adds to Claude is `https://<app>/mcp`, and the issuer is `appUrl()`. Responses are `no-store`.
- **MCP over Streamable HTTP, stateless and JSON only.** Each POST carries one JSON-RPC message (or a 2025-03-26 batch, at most 20) and gets one JSON response. There are no sessions and no server-sent events, so GET answers 405. The server supports protocol versions 2025-11-25, 2025-06-18 and 2025-03-26, and offers only tools. It checks `Origin` (none, its own, or claude.ai, claude.com and anthropic.com) against DNS rebinding. It is hand-written (about 150 lines) rather than the SDK, and was checked against the official TypeScript SDK client (1.32.1): discovery, sign-in, initialize, tools/list, tools/call and ping.
- **The consent page is an app route, as in ADR-051.** The authorization endpoint is `/connect/claude`, behind the usual sign-in, MFA, org and terms guards. The page checks the request (pinned client, exact redirect URI, `response_type=code`, PKCE `S256`, `resource`). A wrong client or redirect shows an error and sends the browser nowhere; any other problem goes back to the client as an OAuth error. The page names where the request came from (claude.ai), and for Claude Code warns that it is an app on this computer, because any local program can use a loopback redirect. Allow calls `connector-authorize` as the signed-in person, which needs a sign-in within five minutes. That records the connection and a one-use code, then redirects back with `code`, `state` and `iss` (RFC 9207). Cancel returns `access_denied`. No cookie session is needed at the authorization server: the Firebase sign-in is the session.
- **Clients are pinned, not registered.** Claude and Claude Code identify themselves with client ID metadata documents (`https://claude.ai/oauth/mcp-oauth-client-metadata` and `.../claude-code-client-metadata`). Their redirect URIs are pinned in `CONNECTOR_CLIENTS` (libs/domain). Claude Code's loopback redirect may use any port (RFC 8252). The server never fetches a URL a request names, and there is no dynamic client registration. Public clients only: `token_endpoint_auth_method` is `none`, and PKCE is required.
- **Opaque tokens, stored as hashes.** A token is `mtc.`, `mta.` or `mtr.` (code, access, refresh), then the org id in base64url, then 256 random bits. `orgs/{orgId}/connectorGrants/{sha256(token)}` holds the kind, connection, person, client, scopes, resource and `expireAt` (Firestore TTL). So a leaked database read yields no usable token. Clients can't read or write grants at all. Codes last 5 minutes and work once. Access tokens last an hour. Refresh tokens last 30 days and rotate on every use; a code or refresh token used twice ends the whole connection (RFC 9700). Every token is bound to its `resource` (RFC 8707). Revoking any token (RFC 7009) ends its connection.
- **Every call re-checks the person.** `resolvePrincipal` runs on each MCP request and refresh. It checks that the connection is active and the member active, with their current role. The sign-in that allowed the connection must not have been signed out everywhere (SEC-04 `sessionsValidAfter`). It must be within the practice's maximum session length (`maxSessionDays`), so a connection lasts no longer than that sign-in would. If the practice requires MFA, that sign-in must have used it. The practice switch and the `integrations.claudeConnector` flag must be on. A practice waiting to be deleted (SEC-05) is read-only. A refusal returns 401 `invalid_token` with the reason, and Claude asks the person to connect again.
- **Each person connects their own Claude, and the practice decides.** `orgs/{orgId}.settings.connector` (`enabled`, `allowProposals`) is off until an owner or admin turns it on in Settings → Claude connector (`connector-setPractice`, recent sign-in). Turning it off ends every connection. Removing or offboarding a member ends theirs. `orgs/{orgId}/connectorConnections/{id}` records each connection (who, which client, scopes, the sign-in it was allowed under, last used). The rules let each person read their own and owners and admins read every one. Only the server writes them. `connector-disconnect` ends one at once. It is allowed while the practice is read-only, because it only takes access away.
- **Read tools give what the person can see, minus privilege and document text.** The tools are `get_my_day`, `search_matters`, `get_matter`, `list_deadlines`, `list_tasks` and `get_time_summary`. Privileged matters, and their deadlines, tasks and time, are left out for every role, even lawyers who can see them in Materia. A privileged matter asked for by number is "not found" to roles without `privileged.view`. Money appears only for roles with `billing.view`. Lists are capped at 50. Results are structured content plus a JSON text copy, with links back into Materia. Record text is described to Claude as data, never instructions.
- **Write tools only suggest (ADR-037).** `propose_task`, `propose_note` and `propose_time_entry` create ordinary suggestion cards on the matter through `proposeSuggestions`. They carry `promptId: 'connector.claude'`, the person as `createdBy` and `requestedBy {uid, name}`, and the card says "Suggested in Claude by …". Someone accepts it in Materia, with the usual permission checks. Suggesting needs the `materia.propose` scope, the practice's `allowProposals`, `clerk.use`, and the action the suggestion would take (`task.edit`, `note.write` or `time.record`). Closed and read-only matters refuse.
- **Everything is audited, nothing is logged.** Every tool call writes `connector.tool_used` to the practice's audit log: which tool, which matter, how many records, and whether it was refused, but not what was asked or returned. Connecting, disconnecting and the practice switch are audited too. Calls are limited to 120 a minute per connection on each instance.

## Consequences

- Nothing new to provision: no secrets, no KMS key, no Cloud Run service. One function and Hosting rewrites.
- What Claude reads leaves Materia and Australia, under the person's own Claude account rather than the firm's agreement with Anthropic. The consent page and Settings say so, and Settings asks the practice to use Claude Team or Enterprise accounts rather than personal ones. Turning the connector on in production is the practice's decision and Blake's, after the wording is reviewed with the legal pages (SEC-01). The flag stays off in prod until then.
- Other MCP clients (ChatGPT, Cursor) can't connect until they are added to `CONNECTOR_CLIENTS` with their published redirect URIs.
- Claude shows the Firebase logo for the connector on a `*.web.app` address. Claude.ai takes a custom connector's icon from Google's favicon service for the last two labels of the server's hostname (`web.app`, which is Firebase's), not from the server (as of October 2026; anthropics/claude-ai-mcp issues 152 and 838). The server still names the Materia logo in `serverInfo.icons` (MCP 2025-11-25), for when Claude reads it. The Materia logo needs a custom domain whose last two labels are Materia's own (a `.com.au` domain shows `com.au`'s icon instead).
- Disconnecting, removing a member, signing out everywhere or turning the practice off takes effect on Claude's next request, because nothing is cached in a token.
- Each MCP request costs a few Firestore reads (grant, connection, member, org) before the tool runs. That's fine at a law firm's volume.
- Suggestions from Claude go through the same accept, edit and dismiss flow as Clerk's, and expire the same way.

## Alternatives considered

- **Dynamic client registration (RFC 7591):** an open registration endpoint lets anyone register a client and redirect URI. Pinning Claude's two clients is smaller and safer, and Claude supports client ID metadata documents.
- **Fetching client ID metadata documents at request time:** that's a fetch of an attacker-chosen URL (SSRF) and a dependency on claude.ai being up. Pinned copies change rarely.
- **JWT access tokens:** they can't be revoked before they expire. Opaque tokens checked on every call let a disconnect take effect at once.
- **The official MCP SDK on the server:** it adds sessions, SSE and a dependency the stateless JSON server doesn't need. It was used to check this one.
- **Including privileged matters for roles that may see them:** privileged material would then sit in a third party's chat history under a personal account. Privileged matters stay in Materia, as Clerk's privilege rules intend.
- **Letting Claude write directly:** that breaks ADR-037. Suggestions keep a person deciding.
