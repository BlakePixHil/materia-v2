## Clerk provider (AI-01, ADR-011a; AI-02a, ADR-011b)

Since AI-02a, Clerk runs on **each firm's own Anthropic API key** (bring your own key). An owner or admin saves it in Settings → Clerk; it is encrypted with the Cloud KMS key `clerk-api-keys` (key ring `materia`, Terraform `modules/firebase_env/security.tf`, 90-day rotation, only `fn-runtime` can use it) and stored in `orgs/{orgId}/integrations/anthropic`, which no client can read.

- The Secret Manager secret `ANTHROPIC_API_KEY` is **unused by the app**: no function declares it, and deploys don't need a version. On **dev** it holds the eval-only key for the Clerk evals (AI-12): the `clerk-evals` workflow reads it as the dev deployer, which has `secretAccessor` on that one secret (Terraform `modules/firebase_env/iam.tf`, dev only). To add it: `printf '%s' "$KEY" | gcloud secrets versions add ANTHROPIC_API_KEY --project=materia-v2-dev --data-file=-`. Use a key from an Anthropic account you control, with a monthly spend limit. Until it exists, the live evals are skipped.
- There is no platform Anthropic account, workspace or spend limit to set up. Each firm's spend limits live in its own Anthropic Console.
- The live smoke test (AI-02a acceptance criterion) needs a real key from an Anthropic account the tester controls: save it in Settings → Clerk on dev, turn on `clerk.enabled` for the org, and call `clerk-hello`.

## Identity Platform (FND-16)

MVP mode: **email and password with TOTP MFA, plus Google sign-in** (Firebase-native). Microsoft SSO is deferred. If the legacy user signs in with Microsoft (MIG-01 will tell), it becomes a must-do item: an Azure app registration (multi-tenant `organizations`) with a redirect URI per auth domain.

Terraform (`modules/firebase_env/security.tf`) manages the following. It ignores `blocking_functions`, which the Firebase CLI registers on deploy:

- email/password sign-in;
- no duplicate emails;
- MFA `ENABLED` with the TOTP provider (SMS off);
- authorized domains.

## Email and push notifications (FND-20, ADR-030, ADR-057)

Notifications email through Resend and push through Firebase Cloud Messaging. Terraform (`modules/firebase_env`) creates the secrets `RESEND_API_KEY` and `RESEND_WEBHOOK_SECRET`, each with the placeholder version `unset`, with access for the functions runtime account, enables `fcm.googleapis.com` and gives the runtime account `roles/firebasecloudmessaging.admin`. Until a real key is set, every email outside the emulator is recorded on its notification as `skipped: not_configured` and nothing is sent; in-app notifications work regardless. One Resend account and domain serve both environments, with an API key and a webhook per environment. Notes:

- **Adopting console-created resources.** `imports.tf` holds `import` blocks driven by `adopt_existing_project`, `adopt_enabled_services` and `adopt_budget_id` in `envs/<env>.tfvars`. Import blocks (Terraform ≥ 1.7) handle `for_each` addresses such as `google_project_service.this["firebase.googleapis.com"]`, and are no-ops once the resource is in state. Nothing was destroyed or replaced: the projects were updated in place (display name `Materia v2 <env>`, labels `app`/`env`; the console's `firebase` labels are kept) and the dev Firebase budget became "Materia v2 dev monthly" (AUD 100, alerts at 50/90/100%).
- **Quota project.** The `google` and `google-beta` providers set `billing_project = var.project_id` with `user_project_override = true`, so a service-account caller's Firebase, Identity Toolkit and KMS calls are billed to the environment rather than the admin project (where those APIs are off). A brand-new environment (staging) needs its project to exist first: `terraform apply -var-file=envs/staging.tfvars -target=module.env.google_project.this`, then a full apply.
- **Prod's original billing account** may still hold the budget Firebase created on the Blaze upgrade ("Firebase Project materia-v2-prod"). It no longer applies to prod's spend; delete it in the console when convenient. Terraform manages "Materia v2 prod monthly" on the current account.
- **Security follow-up.** `terraform-agent` holds a long-lived key with Owner on every project. Once CI applies Terraform through Workload Identity Federation, delete the key (`gcloud iam service-accounts keys list --iam-account terraform-agent@materia-v2-admin.iam.gserviceaccount.com`). The unmanaged `terraform-agent@materia-v2-dev` service account (no keys used here) can also be removed.
