Notes:

- **Adopting console-created resources.** `imports.tf` holds `import` blocks driven by `adopt_existing_project`, `adopt_enabled_services` and `adopt_budget_id` in `envs/<env>.tfvars`. Import blocks (Terraform ≥ 1.7) handle `for_each` addresses such as `google_project_service.this["firebase.googleapis.com"]`, and are no-ops once the resource is in state. Nothing was destroyed or replaced: the projects were updated in place (display name `Materia v2 <env>`, labels `app`/`env`; the console's `firebase` labels are kept) and the dev Firebase budget became "Materia v2 dev monthly" (AUD 100, alerts at 50/90/100%).
- **Quota project.** The `google` and `google-beta` providers set `billing_project = var.project_id` with `user_project_override = true`, so a service-account caller's Firebase, Identity Toolkit and KMS calls are billed to the environment rather than the admin project (where those APIs are off). A brand-new environment (staging) needs its project to exist first: `terraform apply -var-file=envs/staging.tfvars -target=module.env.google_project.this`, then a full apply.
- **Prod's original billing account** may still hold the budget Firebase created on the Blaze upgrade ("Firebase Project materia-v2-prod"). It no longer applies to prod's spend; delete it in the console when convenient. Terraform manages "Materia v2 prod monthly" on the current account.
- **Security follow-up.** `terraform-agent` holds a long-lived key with Owner on every project. Once CI applies Terraform through Workload Identity Federation, delete the key (`gcloud iam service-accounts keys list --iam-account terraform-agent@materia-v2-admin.iam.gserviceaccount.com`). The unmanaged `terraform-agent@materia-v2-dev` service account (no keys used here) can also be removed.
